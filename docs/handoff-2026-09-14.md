## 4. Feature A — create an account from the members UI

**What the owner asked for**: adding a member by email should be able to create the account, instead
of failing when it does not exist.

**What exists today.** `MembersSection` in `src/components/Settings.tsx:327` calls
`addMemberByEmail(workspace.id, email)` → `src/db/api.ts:193` → RPC `add_member_by_email`. That RPC
looks up `auth.users` by normalised email and raises `DA404 'no account with this email on this
origin'` when absent. It **never creates an account**. The mapping `MEMBER_ERR = { DA404:
'members.noAccountHere' }` at `Settings.tsx:299` puts that on screen.

Account creation lives elsewhere, behind a different gate: `LoginsSection` (`Settings.tsx:542`,
admin-only tab) → `createLogin(email, password)` → `src/db/api.ts:251` → RPC
`create_login(email, password, admin default false)`, delegating to `_create_login_impl`
(`supabase/schema.sql:773`). That function raises `DA001` if the caller is not an instance admin,
`DA010` on a malformed email, `DA011` under 8 password chars, `DA012` on a duplicate. It writes
`auth.users` + `auth.identities` directly, `crypt(pw, gen_salt('bf'))`, `email_confirmed_at = now()`.

**The decision to make first, because it is the whole feature**: the two gates differ.
`create_login` is **instance-admin-only**; `add_member_by_email` is **workspace-owner-only**. A
workspace owner who is not an instance admin cannot create accounts at all today. Three options:

1. **Admin-gated inline mint (recommended, no schema change).** In the members form, when the add
   fails `DA404` *and* the current user is an instance admin, reveal a password field and a
   "Create and add" button calling `createLogin(email, password)` then `addMemberByEmail(...)`. Show
   the credential once, exactly as `LoginsSection` does (`minted` state, `swin__minted` block at
   `Settings.tsx:637`), then the admin hands it over out of band. Pure client work: ~40 lines in
   `Settings.tsx`, 3 new i18n keys in `src/i18n/dict.ts` (**both** `ru` and `en` — adding keys is
   allowed, rewording an existing string is not), one stack test. The admin flag is already loaded in
   `Settings` (`const [admin, setAdmin] = useState(false)`, `Settings.tsx:72`, from `isAdmin()`) and
   only needs passing into `MembersSection`.
2. **Let workspace owners mint accounts.** Widens who can create identities on the origin. Changes
   the two-level membership model; needs an ADR before code. Not a UI change.
3. A new spec. Slowest; option 1 is what was actually described.

**Non-negotiables whichever is chosen**: no invite email (no SMTP configured, sign-ups off by
design); the password is never written to Dexie, never logged, never in a URL — it lives in component
state for the duration of the call (see the comment at `Settings.tsx:529`); personal workspaces
unaffected; the server re-checks every guard regardless of what the UI hides.

**Test it as one scenario, not five**: an admin adds an unknown email → account created, member row
present, credential shown once, the new account can sign in; a non-admin owner adds an unknown email
→ `DA404`, nothing created. `tests/stack/logins-provisioning.test.ts` and
`tests/stack/members-two-accounts.test.ts` are the models to copy.

## 5. Feature B — sync local speckit tasks (spec 003, the agent-edit layer)

The fork's stated differentiator. A full spec, plan, data model and two contracts already exist on
`spec/003-agent-edit-layer` @ `3b87c87` — **1110 lines worth keeping**. Only the task list needs
writing, and it was never written.

**The shape**: a `dandori` CLI makes `.dandori/tasks/<uuid>.md` in a project repo a two-way working
copy of one workspace's tasks on one origin. Agents edit the files like source; the CLI pushes them
as ordinary client writes under the existing LWW rule and writes every disagreement to disk as
`<uuid>.conflict.md` rather than resolving it. Six commands: `init`, `login`, `logout`, `pull`,
`push`, `status`. Speckit `tasks.md` ingestion, MCP and the teamlead view are **later consumers of
this layer**, not variants of it — do not build them into v1.

Three properties that make it cheap, all already decided in the plan:

1. **Zero database change** — no table, column, RPC, policy or trigger. The CLI's bookkeeping is the
   same bookkeeping the app keeps in Dexie `meta`, kept in `.dandori/state.json` instead.
2. **One LWW implementation, two clients.** The comparators move out of `src/sync/sync.ts` into a
   pure `src/sync/lww.ts` that both the app and the CLI import. Reimplementing the rule in the CLI is
   the one thing that must not happen — the client merge (`src/sync/sync.ts:409-458`) and the server
   `keep_newer()` trigger (`supabase/schema.sql:142-153`) are one rule with two enforcement points;
   a CLI copy would make it three.
3. **Conflicts are output, not a decision.** No merge model beyond whole-row LWW. `push` exits
   non-zero while any conflict file stands.

Code lives in a new `cli/` directory, a separate Node build target, importing `src/db/types.ts` and
`src/sync/lww.ts`. **It must not be reachable from the browser bundle** — the CLI will grow `fs`/`os`
imports that break the PWA build if they leak. Worth its own test.

`contracts/file-format.md` is the grammar (front-matter key order fixed, a small non-YAML value
subset, unknown keys are a push error, `user_id`/`synced_at`/`deleted`/`_dirty` forbidden, body is
`tasks.description` verbatim, comparison on projected rows and never on file bytes).
`contracts/cli.md` is the command surface. Follow both; they are what keeps a later MCP surface thin
instead of divergent.

## 6. Gotchas that cost this session real time

- **Stack tests share one database.** Running the whole suite in parallel produces failures that
  vanish when a file runs alone — `tests/stack/team-rls-both-halves.test.ts` drops and recreates
  `own_rows` mid-run, breaking whatever else is in flight. Run stack tests **serialized**, or accept
  that a parallel red needs an isolated re-run before it is believed.
- **Uncommitted schema experiments persist in the local DB.** Policies left over from an abandoned
  attempt silently widened access and made a security test pass that should have failed. Re-apply
  `supabase/schema.sql` from a clean checkout before trusting a red or a green.
- **Supabase's `postgres` role is not a superuser.** `current_setting('is_superuser')` is `off`
  there, so an `is_superuser` exemption in a trigger never fires and blocks the harness's own
  cleanup. The working exemption is `auth.uid() is null` — app writes always arrive through PostgREST
  with a JWT, direct DB connections never do.
- **Cloudflare's edge serves a stale asset right after deploy.** A first fetch of a just-deployed
  bundle returned the previous build. Cache-bust before concluding a deploy is wrong. The PWA service
  worker compounds this in real browsers — hard-reload before debugging.
- **`sb_secret_` appears in a clean bundle.** It is supabase-js's own key-prefix check
  (`e.startsWith("sb_secret_")`), not a leaked key. Grep for `sbp_`, `service_role`, `GOCSPX` instead.
- **`users_seed_first_admin` really does fire**, including for an account created in the dashboard.
  The "manual first admin backfill" step is unnecessary on a fresh account.
- **Owner-only controls stay hidden until the seeded owner row is pulled.** Right after creating a
  team workspace while offline, the creator does not yet see owner controls. Known, inherent, not a
  bug to chase.
- `src/components/SignIn.tsx:8` still says accounts are created in the Supabase dashboard. Stale
  comment, no behaviour.

## 7. Process note

Worth one paragraph because it will otherwise repeat. 002 was executed as 63 cards with per-card
receipts, a decision-ledger row per deviation, worktree lanes and reviewer passes. That produced an
auditable trail and a working deployment — and spent a day and an enormous token budget to reach a
feature set a tighter loop would have reached in a fraction of both. The ceremony was sized for a
regulated multi-person project; this is a solo fork racing a demo.

The loop to use instead: **one spec and one scenario test per feature, written once; ~5 parallel
coding agents against disjoint files; green tests are the gate; done; next feature.**

Keep exactly three things from the old process, because each caught a real defect:

1. **Write the scenario test before the code.** It is what proved the server was already correct when
   a reported bug turned out to be a client-validation gap.
2. **Never let an agent self-approve a security-surface promotion.** RLS policies, triggers and
   anything in `supabase/schema.sql` are the one surface that can lose or leak data.
3. **`supabase/schema.sql` has exactly one writer at a time.** It is the real serial constraint;
   conflicts there are semantic, not merge noise.

Everything else — per-card receipts, ledger rows for reversible decisions, per-card closers, the
validation map's STALE cascade — can go. `docs/validation-map.md` has one genuinely useful row left:
`account-provisioning` is HIGH, its tests are green (20/20), and it is still marked UNTESTED because
an agent may not promote it. Promote it or delete the file; half-maintaining it is worse than either.
